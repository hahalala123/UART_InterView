# 代码讲解（小白向）——串口警报实时处理系统

> 目标读者：没有嵌入式/Linux 驱动基础的初学者。
> 读完你应该能：① 向别人讲清楚这套代码的每一部分在干什么；② 理解为什么它快；③ 知道每个文件的作用，能自己改。

---

## 1. 这套代码要解决什么问题？

**原始需求**（来自《串口警报实时处理技术方案》）：

- 两个高速串口（40 Mbaud），各连一个警报器。警报时，串口会收到 **1 个字节**。
- 要求：从"串口收到这个字节"到"用户态程序调用处理函数"的延迟，**平均 < 1 微秒（1 us = 千分之一毫秒 = 一百万分之一秒）**。

**为什么难？** 1 微秒非常短。CPU 1 秒钟执行几十亿条指令，1 微秒大约只够执行几千条指令、或进出内核一两次。传统做法（硬件中断 → 内核处理 → 唤醒用户程序）光"进出内核"就要几微秒，根本来不及。

**方案**：让处理程序（用户态）**死循环盯着串口寄存器看**（术语叫"忙轮询"），一看到"有数据"标志就立刻处理——全程不进内核、不被调度、不被中断打断，延迟 = 最多一个循环周期（百纳秒级）。

**本工程的作用**：在**没有真实硬件**的服务器上，用软件模拟出"串口 + 警报器"，跑通并测量这条路线的延迟。

## 2. 总体架构：一次警报的完整旅程

```
                    ┌─────────────────────────────────────────────┐
                    │  内核态 (valarm.ko 模块, insmod 加载)        │
                    │                                             │
   你执行:          │   valarm_burst_fn() (hrtimer 定时器回调)     │
 echo "1000        │     │ ① 写时间戳 INJECT_TS = 现在的时刻        │
  1000000"         │     │ ② 写字节到 RBR (比如 0x2A)              │
 > /sys/.../burst  │     │ ③ 内存屏障                               │
                    │     │ ④ 置位 LSR 寄存器的 DR 标志             │
                    │     ▼                                       │
                    │   一页物理内存 ("寄存器块")                  │
                    │   ┌──────┬──────┬──────┬──────┬──────┐      │
                    │   │ RBR  │      │ LSR  │  TS  │ CNT  │      │
                    │   │ 0x2A │      │ DR=1 │ 时刻 │      │      │
                    │   └──────┴──────┴──────┴──────┴──────┘      │
                    └───────────────▲─────────────────────────────┘
                                    │ mmap: 同一页物理内存
                                    │ 被映射到用户进程地址空间
                    ┌───────────────┴─────────────────────────────┐
                    │  用户态 (alarmd 进程)                        │
                    │                                             │
                    │   while (!停止) {                            │
                    │       读 LSR, DR==1? ──没有──> 继续循环      │
                    │           │是                               │
                    │       读 RBR = 0x2A  (数据!)                 │
                    │       读 INJECT_TS   (报警时刻 t0)           │
                    │       读现在时刻 t1                          │
                    │       清 DR                                  │
                    │       调用 foo(端口号, 0x2A, t0)  ← 需求!    │
                    │       记录延迟 = t1 - t0                     │
                    │   }                                          │
                    └─────────────────────────────────────────────┘
```

**核心思想一句话**：内核模块申请一页内存扮演"串口寄存器"，用定时器扮演"警报器"往里面写数据；用户态程序通过 `mmap` 获得这页内存的指针，死循环读它——**两边读写的是同一块物理内存，就像两个人共享同一块白板**。

## 3. 必备背景知识（每个概念 3 分钟）

### 3.1 内核态 vs 用户态

CPU 分两种运行模式。用户态程序（你写的普通 C 程序）权限低：不能直接读写硬件、不能访问任意内存、想做特权操作（如操作硬件）必须请求内核代办（**系统调用**）。内核态（操作系统本身 + 内核模块）权限最高。

**为什么本方案强调"热路径零系统调用"？** 因为一次系统调用本身就要几百纳秒到几微秒（CPU 要保存现场、切换权限级别、进内核处理、再切回来）。1 微秒的预算根本不允许每次警报都进内核。

### 3.2 内核模块（Kernel Module）

一段可以动态加载进内核的代码：`insmod xxx.ko` 加载，`rmmod xxx` 卸载，不需要重启。加载时执行 `module_init` 注册的初始化函数，卸载时执行 `module_exit` 注册的清理函数。

本工程的 `kmod/valarm.ko` 就是这样一个模块——它是"模拟硬件"的扮演者。

### 3.3 设备文件与 misc 设备

Linux 习惯用"一切皆文件"访问硬件：`/dev/valarm0` 这样的**设备文件**就是硬件的替身，对它 open/read/write/mmap 就是在操作硬件。

注册设备要告诉内核"这个设备支持哪些操作"——通过一个 `file_operations` 结构体（C 语言里的"虚函数表"）。本驱动只实现了其中一个操作：`.mmap`。

**misc 设备**是内核提供的简易字符设备框架，适合"只有一两个功能"的小设备，不用走完整的驱动模型，几行代码就能注册出 `/dev/xxx`。

### 3.4 mmap 与 MMIO——本方案快的根基

**mmap（内存映射）**是内核提供的一个系统调用：把一段物理内存"挂"进你的进程地址空间，之后你用**普通指针**读写它。

`valarm_mmap()` 做的事：把驱动申请的那页物理内存映射给用户进程。映射完成后：

```c
volatile uint8_t *base = mmap(...);   // 只做一次
// 之后热路径里:
uint8_t status = base[0x05];          // 读"寄存器" = 一次普通内存读, 约几纳秒
```

**MMIO（Memory-Mapped I/O，内存映射I/O）**就是真实硬件的工作方式：ARM SoC 把串口寄存器编址在物理地址空间里，CPU 用读写内存的指令访问它们。我们的模拟用一页普通内存复刻了同样的接口——所以**同一套 alarmd 代码，把 mmap 的目标从 /dev/valarmN 换成真实设备后就能直接上目标板**，这正是框架的价值。

### 3.5 sysfs——用文件和驱动对话

`/sys/` 下的文件是内核对象（驱动、设备）导出的属性。写文件 = 调用驱动提供的写函数，读文件 = 调用读函数。本驱动提供三个：

| 文件 | 方向 | 例子 | 效果 |
|---|---|---|---|
| inject | 只写 | `echo 42 > inject` | 模拟警报器发 1 个字节 0x42 |
| burst | 只写 | `echo "1000 1000000" > burst` | 每 1ms 发 1 个，共 1000 个 |
| stats | 只读 | `cat stats` | 看注入计数 |

### 3.6 中断 vs 轮询

- **中断**：硬件主动"打电话"给 CPU——高效（没事时 CPU 可以干别的），但"接电话+处理"本身有微秒级开销。
- **轮询（polling）**：CPU 不停去看"有没有事"——浪费 CPU（没事时也一直在看），但看到就能立刻处理，没有进出内核的开销。

本系统的约束（平均延迟 < 1us）把中断路线物理上排除了（方案第 2 节有定量论证），所以选轮询。代价是这个 CPU 核被 100% 占用——方案 D3 用"独占一个核"来隔离这种影响。

### 3.7 volatile——防止编译器"自作聪明"

```c
while (base[0x05] & 0x01) { }   // 没有 volatile 时, 编译器会怎么想?
```

编译器看到"反复读同一地址，值没变"，会优化成"只读一次，然后死循环判断这个值"——程序就卡死了。`volatile` 告诉编译器：**这个地址的内容可能被程序之外的力量（硬件/另一个 CPU/内核）改变，每次都必须真的去读内存**。所有 MMIO 访问都必须加 volatile。

### 3.8 内存屏障（smp_wmb）

多核系统里，为了提高效率，CPU 可能"攒一批写操作再一起发出去"（写缓冲）。这会导致：**你先写了数据、再写了标志位，但另一个 CPU 可能先看到标志位、后看到数据**。

内存屏障就是一道"闸门"：`smp_wmb()` 保证**它之前的所有写操作，必须先于它之后的写操作被其它 CPU 看到**。注入函数里"先写数据和时间戳 → 屏障 → 再置 DR 标志"的顺序就是靠它保证的，否则用户态可能读到"标志=有数据、内容却是旧的"这种撕裂状态。

### 3.9 SCHED_FIFO 与绑核

普通线程的调度是"分时"的——时间片到了就被踢下 CPU，_ready 队列里排队的别人先跑。这意味着你的处理线程可能在最不该的时候被换下去（延迟瞬间变成几毫秒）。

`SCHED_FIFO` 是**实时调度策略**：优先级 99 的线程一旦运行，除非自己让出 CPU 或等来更高优先级的线程，否则一直占着 CPU 跑。配合"绑定到某个核"（`sched_setaffinity`）+ 把其它任务从中断和调度中赶出去（`isolcpus` 等启动参数，见技术方案 5.3），实现"这个核就是你的"。

### 3.10 时钟与时间戳

延迟 = t1 - t0，两次取时间。**关键陷阱：时钟域**。Linux 有好几种时钟：`CLOCK_MONOTONIC`（会随 NTP 时间调整被缓慢拨快拨慢）、`CLOCK_MONOTONIC_RAW`（纯净的硬件计数器，谁也别想调它）。如果 t0 和 t1 用了不同域的时钟，差值会包含一个持续漂移的误差。

本框架的统一约定：**两边都用 MONOTONIC_RAW**（内核侧 `ktime_get_raw_ns()`，用户侧 vDSO `clock_gettime(CLOCK_MONOTONIC_RAW)`），同源同速，差值干净。（开发中实测：混用 MONOTONIC 域会有 ~0.84s 基线偏移且漂移——见 SESSION_STATE 坑点 6。）

### 3.11 PLT 懒绑定与预热

动态库（libfoo.so）里的函数，第一次调用时才做地址解析（叫 PLT 懒绑定），而且调用时可能触发**缺页中断**（把磁盘上的库文件读进内存）。这些一次性开销都在微秒级。处理线程如果第一次真正处理警报时才付这笔钱，那一次警报的延迟就爆表了。所以初始化时先空调一次 `foo()` 预热——这正是 alarmd 初始化第 4 步。

## 4. 逐文件讲解

### 4.1 `kmod/valarm.c`（约 300 行）——"硬件扮演者"

按函数讲：

**`valarm_init()`** — `insmod` 时执行。循环两次（两个串口），每次：
1. `alloc_page()` 申请一页物理内存（4KB），当这个串口的"寄存器块"。`__GFP_ZERO` 表示内容清零。
2. `hrtimer_init()` 准备一个内核高精度定时器（后面发突发数据用）。
3. `misc_register()` 注册 misc 设备 → 内核自动创建 `/dev/valarmN`，并把我们在 `file_operations` 里登记的 `valarm_mmap` 挂上钩。
4. 打一条日志（`dmesg` 里能看到）。

**`valarm_mmap()`** — 用户态调用 `mmap()` 时内核最终调到这里。
- 检查映射长度不超一页（**注意：用户请求 0x100 字节，vma 实际覆盖整页 4096，所以与 PAGE_SIZE 比较**——这是实车过的坑）；
- `vm_insert_page()` 把那页物理内存映射进用户地址空间。这是"共享白板"的实现点。

**`valarm_inject()`** — 模拟"警报器发出 1 字节"，四个动作：写时间戳 → 写字节 → 内存屏障 → 置 DR 标志（顺序与屏障的含义见 3.8）。同时累加注入计数和慢路径诊断计数（`IRQ_CNT`，对应方案 D5）。

**`valarm_burst_fn()`** — hrtimer 的回调。被触发时注入一个字节；没发够数量就把定时器推到下一个时间点并返回 `HRTIMER_RESTART`（连发），发够了返回 `HRTIMER_NORESTART`（停）。

**`inject_store()` / `burst_store()` / `stats_show()`** — sysfs 三个文件的读写函数（见 3.5）。`container_of` 那行是从内核框架传给我们的 `device*` 找回自己的 `struct valarm*`——内核 C 代码的惯用手法。

**`valarm_exit()`** — `rmmod` 时执行，倒序释放：停定时器 → 注销设备 → 释放内存。

### 4.2 `user/alarmd.c`（约 260 行）——"处理程序"

按 main() 的执行顺序讲：

**参数解析** `-c 1 -p 99 -o out.csv`：绑 1 号核 / FIFO 优先级 99 / 报告输出路径。

**① 内存锁定 `mlockall()`**：告诉内核"这个进程的所有内存都锁在物理内存里，不准换出到磁盘"。否则热路径中如果访问的页恰好被换出去了，处理一次缺页要几百微秒——又一次延迟爆表。注意要先 `malloc` 好样本数组再锁。

**② 实时属性**：申请 SCHED_FIFO 99（失败则降级并打印警告，功能不受影响，只是延迟数据会差）；绑定 CPU1。

**③ mmap 两个设备**：之后 `g_uarts[0].base` / `g_uarts[1].base` 就是两个"寄存器块"的用户态指针。

**④ 预热**：空调两次 `foo()`（见 3.11）。

**热循环**（灵魂，见 2 的图和 3.6/3.7 的解释）：扫两个口 → 发现 DR 置位 → 读数据、读报警时间戳 t0、取现在时刻 t1、清 DR → 调 `foo()` → 序号检查（字节应连号，不连号 = 丢过数据）→ 存样本。收到 SIGUSR1/SIGINT 时循环退出，打印统计报告并写 CSV。

**`report_and_save()`**：对延迟数组排序，算 avg/p50/p99/max，连同 seq_errors/overflow 一起打印，CSV 里逐条落盘（可用 `tools/stats.py` 画直方图）。

### 4.4 `tools/run_test.sh` — 测试导演

按顺序：清理残留模块 → `insmod` → 启动 alarmd（直接启动不加 sudo，否则信号发不进去）→ 两口各注入 1000 次突发 → 等结束 → 发 SIGUSR1 收报告 → 比对内核计数 → `rmmod` → 打印 PASS。

### 4.5 `tools/stats.py` — 报告美化

读 CSV，输出统计值和 ASCII 直方图（`--hist 20`）。

## 5. 一次 `make test` 的完整时序

```
0.0s  insmod valarm.ko          模块初始化: 申请两页内存, 注册两个 misc 设备
0.1s  /dev/valarm0/1 出现       (节点由 udev 自动创建)
0.2s  alarmd 启动               mlockall → FIFO99 → 绑核 → mmap → 预热 → 进入热循环
1.2s  echo > burst (两口)       hrtimer 开始每 1ms 注入一次
2.2s  突发发完 (1000×1ms)       alarmd 已在每次注入后 ~百ns 内处理完毕
3.7s  kill -USR1                alarmd 退出循环, 打印报告 + 写 CSV
3.8s  cat stats                 内核: injected=1000 ←→ 用户态收到数, 比对
3.9s  rmmod                     模块卸载, 设备消失, 现场干净
```

## 6. 实测结果怎么读（2026-09-21 鲲鹏 ECS 实测）

```
samples      : 1904     ← 两口共收 1904 (注入 2000, 丢 96)
avg          : 511 ns   ← 含 2 次极端离群, 仍 < 1us ✓
p50          : 140 ns   ← 一半的事件在 140ns 内完成处理
p99          : 190 ns   ← 99% 在 190ns 内 —— 远超 < 2us 的验收线
max          : 509 us   ← 云服务器调度 stall, 非框架问题
seq_errors   : 2        ← 丢失集中在 2 个簇 (stall 期间字节互相覆盖)
```

**结论**：典型延迟 140~190ns，落在技术方案第 4 节预算的"轮询发现 + 取数"区间内，**验证了"用户态 MMIO 忙轮询可达亚微秒"这一核心论断**。max/丢字节由共享云服务器的 steal time 造成，嵌入式目标（独占核）不会有。

## 7. 常见问题（FAQ）

**Q: 用户态直接读写硬件，安全吗？**
A: 这是嵌入式专属做法。设备节点权限（crw------- root）控制了谁能开；方案面向的是专用设备而非通用系统。

**Q: 轮询 100% 占一个核，不浪费吗？**
A: 这是用 CPU 换延迟的典型权衡。方案的前提是"系统上不运行其他业务"，且明确用 isolcpus 把轮询核隔离出来。

**Q: 真实硬件上怎么用这套代码？**
A: 换掉驱动层：设备树加 `generic-uio` 节点用主线 `uio_pdrv_genirq` 替代 valarm.ko，alarmd 打开 `/dev/uioN` 即可，用户态代码零改动（README 最后一节有清单）。

**Q: 为什么字节序号能查丢包？**
A: 注入器按 0,1,2,...255,0,1... 循环编号。连续两次读到的字节若不是 +1 关系，说明中间有字节没被及时取走、被新字节覆盖了。

**Q: INJECT_TS 时间戳在真实系统中对应什么？**
A: 对应方案 7.1 通道一的"示波器 t0"——真实硬件可用 GPIO 边沿或 UART 的硬件时间戳捕获；模拟框架由内核在注入瞬间锁存，等效。
